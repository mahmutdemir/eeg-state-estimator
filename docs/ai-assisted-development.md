# AI-assisted development

This repository was written with substantial help from an AI coding assistant. This page
describes how, because "we used AI" is not a useful statement on its own — what matters is
which tasks were delegated, what the review gate was, and how the verification was kept
from being generated by the same process it is meant to check.

It is written as an engineering-practice note, not a disclaimer.

## The rule that does the work

**A test must exist, and must have been observed to fail, before generated code is
accepted against it.**

Not "tests were written". *Run, and seen red.* The distinction matters: a test written
after the implementation, against the implementation's actual behaviour, mostly asserts
that the code does what it does. A test written first, from the requirement, can disagree
with the implementation — and several here did.

The git history shows this rather than claiming it. Commits labelled `test(...)` land
before the `feat(...)` commit that satisfies them, and the test commits have failing CI.
That is not untidiness; it is the evidence. `test(synthetic): oracles for the generators,
before the generators` is red on purpose.

## What was not delegated

**The requirement tolerances.** Every numerical acceptance criterion in
[`requirements.md`](../requirements.md) was *measured* before being written down, not
reasoned about and accepted. This was not a formality. Three of the first draft's
tolerances were wrong:

- White-noise PSD flatness was specified as ±10% bin-to-bin. That is unsatisfiable by any
  correct multitaper implementation — the per-bin relative standard deviation is `1/√K` =
  38% by design, and measurement gives 200–236% regardless of record length. Had it been
  accepted, the first correct implementation would have appeared to fail.
- Parseval was specified as ±2% against the time-domain variance of white noise. That
  measures the sampling error of a variance estimate, not the normalisation: 2.76% at a
  4-second record, so the requirement fails while the code is right.
- Peak frequency was specified as recoverable by `argmax`, justified by "the worst-case
  error is half a bin". The justification was wrong — multitaper averaging produces a flat
  plateau whose argmax error scales with the analysis bandwidth, not the bin width — and
  the measured error exceeded a full bin at a 4-second record.

Each is recorded in [`design-decisions.md`](design-decisions.md) with the measurement. The
general point: an AI assistant will produce a confident, plausible tolerance, and a
plausible tolerance that has never been run is a liability, because it will be discovered
by a failing test later and quietly loosened to make the suite green.

**The filter recursion.** The scalar Kalman predict/update loop in
[`kalman.py`](../src/eeg_state_estimator/statespace/kalman.py) was derived and written by
hand, in a separate exercise, and checked against two closed-form oracles — that `Q = 0`
reduces exactly to recursive inverse-variance weighting with `P_k = 1/(1/P₀ + k/R)`, and
that the posterior variance converges to the Riccati fixed point
`p = (Q + √(Q² + 4QR))/2` — before any of it was brought into this package.

The assistant's contribution to that module was packaging: types, the streaming-shaped
API, the dataclasses, and one numerical change (the covariance update form, discussed in
`design-decisions.md`). The arithmetic is the author's.

This was deliberate. Keeping the derivation and implementation aligned makes the
filter's numerical assumptions easier to inspect and maintain.

## How verification was kept independent of generation

Three structural separations, in increasing order of how much they matter:

**1. The oracles come first, and are tested on their own.** `tests/synthetic/generators.py`
has its own test file, written and passing before anything that consumes it.
`test_power_law_amplitude_spectrum_is_exact` inspects FFT magnitudes directly, with no
spectral estimator involved — so a failure cannot be blamed on code that did not exist yet.

**2. Tests assert against closed-form answers, not against reference implementations.**
Comparing two implementations proves they agree, which is exactly what you get for free
when one process writes both. Comparing against a derivation — `A²/2`, Parseval, the
Riccati root — proves correctness independently of who or what wrote the code.

**3. The diagnostics are verified against known distributions, never against the filter.**
`tests/statespace/test_diagnostics.py` does not import the Kalman filter at all. Ljung-Box
is calibrated on iid Gaussian noise and powered on an AR(1); the chi-square bounds are
checked against `scipy.stats.chi2`; coverage is checked on draws whose coverage is known
by construction. A diagnostic validated only by pointing it at the estimator it is meant
to check can agree with a broken estimator and silently bless it.

**And each diagnostic is shown to reject a knowably wrong filter** (REQ-037) — process
variance 10× too small, 10× too large, observation variance mis-scaled. A suite that only
ever reports PASS is indistinguishable from a suite of `assert True`, and an AI-assisted
suite is especially prone to that failure, because generating tests that pass is easier
than generating tests that discriminate.

## What the process actually caught

Listed because the value of a review gate is only visible in what gets through it. All of
these were assistant-generated and wrong:

| Defect | How it surfaced |
|---|---|
| Traceability scanner used a regex and counted marker-shaped text inside *string literals* in test fixtures — a requirement could appear covered by a test that only quoted its ID | Its own test, which is why the scanner now parses the AST |
| Three requirement tolerances unsatisfiable or statistically fragile (above) | Measured before any test was written against them |
| A "no peak" test built on white noise, which can perfectly well have an interior maximum in a narrow window | Failed on first run |
| A hand-built flat spectrum on a `linspace` grid whose points did not land on the band edges being integrated between | Failed on first run |
| A conditioning test comparing the posterior variance to its limit `R` rather than to the exact `P₀R/(P₀+R)` | Failed on first run |
| A throwaway function written solely to keep an unused import alive | Caught in review before commit |

The pattern is worth naming: the assistant's *code* was mostly right and its *test
premises* were the weak point. Three of the six above are cases where the test encoded an
assumption that sounded reasonable and was false. That is an argument for deriving
acceptance criteria from first principles and measuring them, rather than for trusting
either the code or the tests because they agree with each other.

## Honest limitations

- **This is not a regulated development process.** It borrows the shape of one —
  numbered requirements, traced tests, recorded design rationale — but there is no quality
  management system behind it, no design history file, no independent reviewer. The claim
  is that the author knows what that evidence looks like and can produce it, which is
  narrower than having worked under it.
- **The traceability scan cannot see dynamically applied markers.** Every marker here is a
  literal decorator and the undeclared-ID test catches typos, but it is a static analysis
  and a sufficiently clever test could hide from it.
- **Coverage of the *requirements* is complete; coverage of the *code* is not measured.**
  Every requirement has a test. That is not the same as every branch being exercised.
- **The multitaper estimator has a dynamic-range limit.** On a spectrum spanning more than
  roughly 70 dB within the analysis band, taper sidelobe leakage forms a pedestal under the
  high-frequency bins and flattens a slope fit. Adaptive (Thomson eigenvalue) weighting
  would improve this and is not implemented.
